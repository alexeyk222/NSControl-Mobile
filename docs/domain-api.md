# API интеграции доменного ядра

Точка входа в ядро на чистом Dart: `package:nscontrol/logic/domain.dart`. Время наблюдения передаётся в **целых микросекундах монотонного секундомера сеанса**. Календарное время и часовой пояс используются только в API сна и рекомендаций. Конструкторы проверяют сохранённые числовые данные; некорректные значения вызывают `ArgumentError` или `FormatException`. Контроллер должен обработать такую ошибку повторной калибровкой или восстановлением настроек по умолчанию.

## Камера и калибровка

`DetectorCapabilities.mlKit` обозначает `mlkit_face_detection` версии `0.15.1` с допустимым абсолютным горизонтальным поворотом лица для оценки глаз не более 18°. Другие движки должны сообщать собственные идентификатор, версию и возможности; профиль другого движка повторно использовать нельзя.

`FaceMeasurement({int? trackingId, double? leftEye, double? rightEye, double? pitchDown, double? yaw, double? roll})`. Вероятности находятся в диапазоне [0,1], углы задаются в градусах. Перед вызовом ядра адаптер нормализует знак наклона: **наклон вниз положителен**. Отсутствующие и неконечные значения делают соответствующий канал недоступным. Изображения лиц и геометрические типы Flutter в этот API не передаются.

`CalibrationCollector({required int trackingId, required DetectorCapabilities detector, required bool hiddenEyes, required int startedUs})`. Вызывайте `add({required int capturedUs, required List<FaceMeasurement> faces})` для каждого своевременно обработанного кадра; пропущенные кадры камеры не считаются обработанными. После 10 секунд и завершения обработки своевременных кадров этого окна вызовите `finish({required int nowUs})` → `CalibrationResult` с полями `profile` (может быть `null`), `issues`, `processedFrames`, `usableFrames`. Сборщик принимает только кадры, полученные в первые 10 секунд; при недостаточном результате нужен новый сборщик. Неизменяемый `CalibrationProfile` сохраняется и восстанавливается через `toJson`/`fromJson`.

Значения по умолчанию конструктора `AlgorithmSettings`: `eyesClosedUs=1500000`, `headDownUs=2000000`, `pitchThreshold=20`, `headYawLimit=30`, `hiddenEyes=false`, `volume=1`, `vibration=true`, `showPreview=true`. `toJson`/`fromJson` используют именно эти имена полей. Изменение параметров алгоритма требует нового экземпляра движка наблюдения, нового сеанса и соответствующего режима калибровки.

## Наблюдение

`ObservationEngine({required String sessionId, required CalibrationProfile calibration, AlgorithmSettings? settings})`.

- `process({required String sessionId, required int capturedUs, required int completedUs, required List<FaceMeasurement> faces})`.
- `tick(int nowUs)` вызывается независимым таймером каждые 50 мс, в том числе при отсутствии кадров.
- `acknowledge({required Set<String> eventIds, required int nowUs})` подтверждает только переданные идентификаторы активных событий, показанных в момент касания.
- `stop({required int nowUs, EventEndReason reason = EventEndReason.observationStopped})` останавливает наблюдение немедленно; при необходимости используйте причины `tripEnded` или `cameraStopped`.

Каждый вызов возвращает `ObservationUpdate`: неизменяемый снимок `snapshot`, списки событий `started`, `ended`, `acknowledged`, переходы `transitions` и признак `rejected` для отброшенных результатов. Текущее состояние доступно через `engine.snapshot`. `ObservationSnapshot` содержит `eyes`, `head`, `activeEvents`, `cameraStatus`, `requiresRecalibration`, `stopped`, `hasUnacknowledgedAlert`. `ChannelSnapshot` содержит `channel`, `available`, `phase`, `reason`, `signStartedUs`, `activeEvent`, `lastUsableUs`.

`ObservationEvent` содержит `id`, `sessionId`, `type` (`eyesClosed`/`headPitchDown`), `signStartedUs`, `thresholdUs`, `alertRequestedUs`, а также необязательные `acknowledgedUs`, `endedUs`, `endReason`. Коды журнала доступны через `.code` соответствующих перечислений, представление в виде словаря — через `toJson()`. Сохраняйте события из `started`, затем обновляйте каждое событие, возвращённое в `ended`/`acknowledged`. Первичное оповещение телефона и часов о камерном событии запускается только для `started`. После каждого обновления определяйте необходимость звука по `hasUnacknowledgedAlert`.

Несовпадение идентификатора отслеживания или неоднозначный выбор лица устанавливают блокировку `requiresRecalibration=true`: требуются повторное подтверждение лица, новая калибровка и новый движок. Пустой список лиц сбрасывает каналы, но допускает возвращение того же отслеживаемого лица. Отсутствие идентификатора отслеживания блокирует движок. Контрольный таймер и непригодные измерения очищают историю медианного фильтра и текущий отсчёт каждого затронутого канала; активное событие завершается с отдельной причиной потери данных. Кадр ровно через 300 мс после последнего пригодного принимается; разрыв **более** 300 мс вызывает сброс. Первые два пригодных кадра после сброса заполняют фильтр, оценка признака начинается с третьего. Длительности обнаружения и восстановления отсчитываются от первого подходящего **отфильтрованного** наблюдения; начало не переносится на время до готовности фильтра.

## Сон и рекомендации

`SleepRecord({required String source, required String sourceId, required DateTime start, required DateTime end, SleepStage stage = SleepStage.asleep})`. Стадии: `asleep`, `core`, `deep`, `rem`, `awake`, `inBed`. `toJson`/`fromJson` сохраняют даты в формате ISO. Используются завершённые записи; продолжающиеся интервалы исключаются при нормализации. При повторе идентификатора записи одного источника применяется последнее вхождение, поэтому хранилище должно возвращать записи с уже применёнными обновлениями.

`SleepNormalizer.summarize({required List<SleepRecord> records, required DateTime now, required String? selectedSource, required SleepReadStatus readStatus, DateTime? lastSuccessfulRead, SleepCoverage? coverage})` возвращает `SleepSummary`: `duration`, `complete`, `dataStatus`, `source`, `windowStart`, `windowEnd`, `readStatus`, `lastSuccessfulRead`, `inputFingerprint`, `recordCount` и итоговые `intervals` после объединения сна и вычитания бодрствования. Статусы чтения: `success`, `unavailable`, `permissionDenied`, `failed`. Интервалы бодрствования вычитаются даже тогда, когда поставщик также возвращает охватывающий их интервал сна. Нахождение в постели без сна исключается. Разные источники не суммируются. Порядок входных записей не влияет на результат, кроме применения обновлений с одинаковым идентификатором.

Для подтверждения полноты сначала рассчитайте сводку, затем сохраните `SleepCoverage({required source, required start, required end, required confirmedAt, required bool hasUnrecordedSleep, required String inputFingerprint})`, используя окно и отпечаток входов текущей сводки. `toJson`/`fromJson` сохраняют подтверждение покрытия. Покрытие не может распространяться на время после его подтверждения. Требуются одновременно полное покрытие окна, отсутствие незаписанного сна, совпадение источника и входов, успешное чтение и хотя бы одна запись сна. При сдвиге окна за пределы подтверждённого интервала полнота снимается. При ошибке обновления сохраняйте прежние записи и время последнего успешного чтения, но пересчитывайте результат со статусом ошибки. Отпечаток представляет собой канонический JSON относящихся к окну записей; хеширование с возможными коллизиями и отметки времени повторной синхронизации не используются.

`RecommendationEngine({required String tripId})`. Для каждой поездки создаётся один экземпляр; `evaluate({required DateTime localNow, required SleepSummary sleep, SelfAssessment assessment = SelfAssessment.unknown, bool tripStarted = false, bool eyesEventOccurred = false, bool headEventActive = false})` возвращает `RecommendationUpdate(recommendation, changed, shouldNotify)`. Вызывайте метод по минутному таймеру и при изменении входов или камерных событий. Перед этим всегда пересчитывайте сводку сна на текущее время. Переданное местное время должно учитывать текущий часовой пояс пользователя; длительности сна рассчитываются по абсолютным моментам UTC.

`SelfAssessment`: `unknown`, `notSleepy`, `sleepy`. Контроллер хранит явный ответ пользователя для текущей поездки и передаёт его при каждом расчёте. После первого `eyesEventOccurred: true` основание по закрытию глаз сохраняется до `endTrip()`. Основание по наклону головы действует при активном головном событии и не обозначается как подтверждённый сон.

`Recommendation` содержит `id`, `tripId`, `action`, `priority`, `reasons`, `reasonTexts`, `message`, `dataMessage`, `dataStatus`, `assessment`, `sleep`, `evaluatedAt` и `toJson`. Действия по возрастанию приоритета: `noGrounds` (0), `reconsiderTripTime` (1), `checkCondition` (2), `delayAndRest` (3), `stopAndRest` (4). Основания имеют стабильные значения `.code`. `shouldNotify` равен `true` только при первом появлении рекомендации с действием или повышении приоритета действия. Изменение основания при прежнем приоритете обновляет отображаемое состояние без повторной вибрации. Контроллер должен объединять новое событие закрытия глаз и связанную рекомендацию в одном оповещении часов. Повторный расчёт сохраняет идентификатор рекомендации, если действие, основания, статус достаточности и использованные значения не изменились; возвращаемое `evaluatedAt` обновляется всегда.

## Принятые решения и проверка

- 15.10.2026: начало признака и восстановления определяется по времени отфильтрованных наблюдений; медиана трёх измерений недоступна до получения всех трёх. Это явно учитывает задержку фильтра и не приписывает результат времени до фильтрации.
- 15.10.2026: для глаз проверяется абсолютный горизонтальный поворот, для головы — поворот относительно калибровки. Проверки выполняются по исходным измерениям до фильтрации, поэтому непригодность одного канала не отключает другой.
- 15.10.2026: для восстановления обе отфильтрованные оценки глаз должны быть не меньше T. Открытие одного глаза прерывает ещё не достигший порога отсчёт закрытия, но само по себе не завершает активное событие. Неоднозначность или смена лица во время калибровки окончательно отклоняет текущий сборщик и требует повторного подтверждения. При сравнении MAD применяется арифметический допуск 1e-12 только на десятичной границе 0,15.
- Наборы граничных тестов, разработанных методом TDD, находятся в `test/logic/`. Производительность устройств, фактический знак наклона, задержки камеры и часов проверяются отдельно на оборудовании.
